# 内网服务器环境记录（172.16.43.126）

> 探测时间：2026-11-13 ~ 11-14
> 探测方式：堡垒机 DAS-USM 网页终端（`SSH sysmgr`），只读命令
> 用途：日后重装、迁移、排障、换人接手时，不必再重新摸一遍环境
> 结论先行：**这台机器是别人的 Docker 生产机，我们只能"加一套隔离容器 + 一个独立端口"，不能动现有任何服务**

## 一、接入方式（先看这段，否则连不上）

| 项 | 实际情况 | 影响 |
|---|---|---|
| 接入通道 | 浏览器打开堡垒机 → 资产列表 → `售水压力监控系统(污水)` → `SSH sysmgr` | 只有**网页终端**能用 |
| 本机 VPN | aTrust 连的是**另一个办公 VPN**，且是**应用级代理**（只代理浏览器进程） | WinSCP / Xftp / Xshell / scp **全部不可用** |
| 实测不可达 | `172.16.43.126:22/443`、`172.56.11.11:22/443/80` 从开发机 **全部不通** | 不要在这些地址上浪费时间调试 |
| 「运行下载」菜单 | 只有 SecureCRT / Xshell / XFTP / Crate / itp / OpenSSH，**没有 WinSCP** | Xftp 配置是 `.xfp` 会话文件（463 字节），不是安装包 |
| 提示"需安装安 trust 客户端" | 本机**已装**（有 `aTrustVNIC` 网卡），但代理的是另一个 VPN | 无法用它打通到这台服务器 |
| 传文件 | 走堡垒机网页终端自带的**文件传输**功能 | 已验证可用 |

**关键教训**：从开发机（本机）到 `172.16.43.126` 的 22/443 **不通**，WinSCP / scp / Xshell 这类客户端在此环境全部无效，唯一通道是堡垒机网页终端 + 它自带的文件传输。

> **2026-11-15 更正**：早前这里写过"`172.16.43.126` 是代理入口，服务器真实地址是 `172.56.43.126`"，该结论**有误**，`172.56.43.126` 这个地址已作废。用户实测 **浏览器访问 `http://172.16.43.126:18080` 可直达本机**，即 `172.16.43.126` 就是这台服务器在办公网内的地址。开发机 ping 不通它属正常现象（本机 aTrust 连的是另一个 VPN，不在同一网段），**不代表别人访问不了**。

## 七、三个必须记住的坑

1. **`lower_case_table_names` 必须为 1**
   开发机 MySQL 9.7.1 的 `lctn=1`，表名实际全小写；但代码里有 **11 个 `__tablename__` 带大写**（`CLdui`、`LeakFile`、`celouTb`、`cl_cxTP` 等）。Linux 默认区分大小写，会导致**找不到表，且 `create_all` 另建同名空表**——页面正常、数据全空。容器启动参数已显式 `--lower-case-table-names=1`。

2. **`PASSWORD_PEPPER` 不能用新值**
   `sswhl_new.sql` 里的密码哈希是按开发机 pepper 算的。换新值 = 所有人登录失败。`install.sh` 检测到已有 `.env` 会保留原值。

3. **`UPLOAD_DIR` 不能留空**
   `Path(settings.UPLOAD_DIR).resolve()` 空值等于当前工作目录，附件会散落到 `backend/` 下。宿主机方案固定 `/opt/sswhl/backend/uploads`；容器方案固定 `/app/backend/uploads`。

## 十、营业所网段与 Docker 网桥撞段（2026-11-17，已定位）

**现象**：部署 Docker（sswhl-mysql）后，岛外（172.17.209.x）及各营业所（全部在 172.17.0.0/16 内）连服务器 172.16.43.126 都 ping 不通；部署前正常。

**根因（2026-11-17 现场确认）**：是我们自己的 compose 网络 `sswhl_net` 被自动分配了 `172.17.0.0/16`（网桥 br-f7354...），与营业所网段完全重叠。服务器收到来自 172.17.x.x 的包后，回包路由查找命中 `172.17.0.0/16 dev br-f7354...`，被送进网桥黑洞（ARP 解析不出，静默丢包）。该机 docker0 在 192.168.70.0/24（linkdown），xinkong_app 在 192.168.71.0/24，均与撞段无关。

**修复**（服务器上操作，挑非业务时间，重启 docker 会让 xinkong 容器短暂中断）：
1. `/etc/docker/daemon.json` 设置 `"bip": "10.212.0.1/24"` + `"default-address-pools": [{"base": "10.213.0.0/16", "size": "24"}]`，彻底避开 172.16.0.0/12（若已有 daemon.json 需合并、勿覆盖）。
2. `docker compose down && up -d` 重建 sswhl_net（compose 已改为显式 `subnet: 10.213.1.0/24`）。
3. 验证：`ip route` 无 172.17 开头路由；`ip route get 172.17.209.x` 走 eth0 网关；岛外能 ping 通并打开 `http://172.16.43.126:18080`。
