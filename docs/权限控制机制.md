# 用户访问权限控制机制

新模块开发时,用户能不能访问某个功能,由一套现成的权限链路控制。本文说明这套机制的原理和新模块的接入方法。

## 机制概览:三层结构

### 1. 数据层(权限从哪来)

- 权限是一条条**权限码**,如 `system:user:manage`,存在 `permissions` 表。
- 权限码挂在**角色**上(多对多),用户通过被分配的角色获得权限。
- `admin` 是超级管理员(`is_superuser=True`),**天然拥有所有权限**,不需要勾选。
- 全部权限码在 `backend/scripts/init_db.py` 的 `DEFAULT_PERMISSIONS` 里登记,重跑 init_db 时自动补进数据库。

```python
DEFAULT_PERMISSIONS = [
    ("system:user:manage", "用户管理", "系统管理"),
    ...
]
```

### 2. 后端校验(真正的安全防线)

`backend/app/api/deps.py` 提供两个依赖:

- `Depends(get_current_user)` —— 只要求登录(校验 JWT、账号未停用);
- `Depends(require_permission("权限码"))` —— 超管直接放行;否则检查用户角色是否挂有该权限码,没有返回 403。

接口上加一行依赖即完成控制:

```python
@router.post("")
def create_vehicle(
    data: VehicleIn,
    db: Session = Depends(get_db),
    _user: User = Depends(require_permission("vehicle:manage")),  # ← 权限控制就这一行
):
```

**后端校验是权限的真正落点。** 前端隐藏菜单只是为了不让用户看到进不去的入口;任何绕过前端的请求,最终都靠后端 403 挡住。新接口无论多简单,必须挂后端校验。

### 3. 前端控制(体验引导,不是安全)

- **菜单**:`src/layout/MainLayout.vue` 的 `menuItems` 里用 `auth.hasPerm('权限码')` 决定菜单项是否出现;
- **路由**:`src/router/index.js` 路由的 `meta.perm` 配权限码,守卫里没权限访问会被踢回 `/dashboard`;
- **按钮级**:页面内用 `v-if="auth.hasPerm('xxx:yyy')"` 控制按钮显示。

用户权限来自登录/`/auth/me` 接口返回的 `permissions` 数组,存在 Pinia(`src/stores/auth.js`)。给用户换了角色后,重新登录或刷新页面生效。

## 新模块接入模板(车辆管理已按此实现,可直接照抄)

1. **登记权限码**:业务模块登记一对 `("模块:view", "模块查看", "分类")` 与 `("模块:manage", "模块管理", "分类")`(第三项用于权限界面分组),重跑 `python -m scripts.init_db`(幂等,只补缺的)。不登记的话,「角色权限」页面的勾选列表里看不到它。
2. **后端路由**:`app/api/routes/vehicle.py`,入口与日常操作(列表/详情/字典/统计/导出/增删改/年检/出险登记)挂 `require_permission("vehicle:view")`,管理操作(删除车辆/报废/图片附件上传删除)挂 `require_permission("vehicle:manage")`;写操作统一加部门范围兜底 `_check_visible`;在 `main.py` 里 `include_router`。
3. **前端页面**:`src/api/vehicle.js` 封装接口,`src/views/vehicle/VehicleManage.vue` 写页面;日常按钮用 `canOperate`(=`vehicle:view`),删除/报废/图片按钮用 `canManage`(=`vehicle:manage`) 显隐。
4. **挂路由和菜单**:`router/index.js` 加路由并带 `meta: { perm: 'vehicle:view' }`;`MainLayout.vue` 的 `menuItems` 加 `if (auth.hasPerm('vehicle:view')) items.push(...)`。
5. **授权**:管理员在「角色权限」页面把「车辆查看」「车辆管理」勾给角色,再分配给用户。只勾 view 的用户是只读身份。重新登录(或刷新页面)后生效。

## 粒度约定

- 业务模块统一采用 `模块:view` / `模块:manage` **两级**:`view` = 页面入口 + 日常操作(查询、图表、导出、常规增删改、年检/出险登记等),`manage` = 批量删除、报废、附件上传、Excel 导入这类管理操作。系统管理类模块仍用单个 `system:x:manage`。只勾 `view` 的用户可完成日常业务,但看不到管理按钮,后端对应接口同样拦截。
- 某模块需要更细时(如导出报表单独控制),再加 `vehicle:export` 这类权限码:前端按钮 `v-if="auth.hasPerm('vehicle:export')"` 隐藏,后端对应接口同样挂 `require_permission`。**权限码先在 DEFAULT_PERMISSIONS 登记**,套路同上。
- 命名统一为 `模块:动作`,全小写英文,冒号分隔。

## 例外:手机管理模块多一个回收码(2026-11-09)

手机管理(`/phone`)在 `view/manage` 之外增加 **`phone:huishou`**,对应旧系统 `bb_user.otherqx` 含「手机管理」标签的人才能把手机状态批量改为「已回收」。旧系统另有 `admin` 侧操作(批量删除、确认报废、显示确认人/日期列),新系统落在 `phone:manage`。落地为:菜单/路由/日常操作/附件/回收登记挂 `phone:view`,`phone:manage` 控批量删除与确认报废,`phone:huishou` 控「已回收」状态选项与 `POST /api/phones/batch-status` 的对应校验。

## 例外:车辆维修模块多一个审批码(2026-11-09)

车辆维修(`/repair`)在 `view/manage` 之外增加 **`repair:audit`**:旧系统用 `bb_user.clsp=1` 的「车辆审批人」单独控制维修单审批/取消审批,不是所有能录入的人都能审批。落地为:菜单/路由/日常增删改/明细/图片/导出/图表挂 `repair:view`,删除维修单挂 `repair:manage`,审批按钮与 `POST /api/repairs/audit` 挂 `repair:audit`;前端通过 `/api/repairs/dicts` 下发的 `perms` 控制审批按钮显隐。

## 例外:加班申请审批模块(2026-11-08)

加班模块**不走**上面的 `view/manage` 两级,而是 5 个权限码 + 页面内 Tab 级显隐,原因是旧系统 6 个 Tab 的权限粒度不同(我的加班人人可用,申请单/核销/汇总/配置各有管控),两级不够用。

| 权限码 | 名称 | 控制范围 |
|---|---|---|
| `overtime:view` | 加班申请查看 | 模块基础可见性 |
| `overtime:apply` | 加班申请单管理 | 申请单管理 Tab、生成/编辑/删除申请单、待汇总记录 |
| `overtime:verify` | 加班核销管理 | 核销管理 Tab、批量核销/反核销/退回草稿、补休登记 |
| `overtime:hr` | 加班汇总管理 | 加班汇总 Tab、汇总导出与 Excel 匹配 |
| `overtime:manage` | 加班模块管理 | 配置管理 Tab(人员池/部门树/审批层级/审批人/审批流开关) |

接入差异(照抄时不要套用「新模块接入模板」):

- **菜单和路由不设权限门槛**:旧系统「我的加班」对全员开放,`MainLayout.vue` 无条件 push 菜单,`router/index.js` 的 `overtime` 路由不写 `meta.perm`。
- **Tab 显隐由后端下发**:`GET /api/overtime/dicts` 返回 `perms`(`is_admin` / `is_verifier` / `is_hr` / `is_approver` / `can_apply` / `can_verify` / `can_summary` / `can_config`),`OvertimeApply.vue` 用它决定 6 个 Tab 的 `v-if`,并在记住的上次 Tab 不可见时回退到第一个可用 Tab。
- **后端校验入口**:`app/services/overtime_common.py` 的 `has_any_perm` / `ensure_perm` / `is_admin` / `is_verifier` / `is_hr`;`overtime_flow.py` 的 `_ensure_verify()` 统一守核销与补休三接口,`overtime_config.py` 的 `_admin_only()` 守配置写接口。超管自动全通过。
- 「我的审批」Tab 不对应独立权限码:按 `overtime_apply_approval.approver_id == 当前用户` 且 `status='pending'` 是否有数据来显示,避免给每个普通用户额外授权。

## 例外:SIM 卡管理(2026-11-09)

SIM 卡管理(`/simcard`)沿用两级权限:`simcard:view` 管模块入口、列表/历史/月度话费/导出/模板下载;`simcard:manage` 管新增、编辑、删除以及全部 Excel 上传(上传模板/批量状态/话费/核对文件),对应旧系统菜单权限「sim卡管理」。旧系统删除只允许登记人或管理人操作,新系统保留该规则(超管除外),即使拥有 `simcard:manage` 也不能删除别人的卡号。

工单信息录入(`/gongdan`)沿用两级权限:`gongdan:view` 管模块入口、字典/部门下拉、列表与全部筛选、导出、新增与编辑、工作内容和材质字典选项删除、抢修班组名单增删改、工单号带出与工单详情抽屉(旧页面无任何角色判断,仅由菜单控制访问,日常操作人人可做);`gongdan:manage` 只管**物理删除工单材料记录**(不可恢复),超管自动拥有。后端 `POST /api/gongdan/del` 独立校验并返 403,不依赖前端显隐;前端无 manage 时点击删除给出提示。
