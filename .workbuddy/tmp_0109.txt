1 文档简介
1.1 文档概述
本开发手册对工单接口API进行详细的描述，通过该指南可以对本系统有全面的了解，使技术人员尽快掌握本系统的接口，并能够在本系统上进行开发。
1.2 总体说明
这是96303热线系统（以下简称热线）提供的http接口。请求参数组装为JSON形式；返回结果是另一个JSON形式。
目前只有一个接口，将来可能逐步扩展多个接口。以下“接口格式”章节描述这些接口的通用格式，“接口详情”章节描述每个接口的参数定义。
2接口格式
2.1 请求地址说明
请采用http post提交请求，例如（仅举例非实际）：
http://172.16.73.91:21000/intf/cxGongDanById
请求报文和响应报文的内容采用utf-8编码。
2.2 请求报文格式
请求模式：按照POST方式，参数组织为json格式字符串
请求报文由两部分组成：
一、公共部分：appId、version这些必填参数
二、业务数据：具体业务的数据内容data，由key/value组成
参数说明如下：
关键字
| 名称
| 备注
|
appId
| 报文请求方身份标识
| 服务端分配给发起方的标识
|
version
| 接口版本号
| 对应接口文档版本号，以便双方跟踪调查
|
data
| 业务数据
| 由key/value组成的集合；不同业务场景有不同的约定，具体看接口详情
|
appId，作为请求方的身份标识，建议采用类似UUID的32位字符串，由服务端分配；服务端收到请求时先检查appId是否合法，避免非法调用；一段时间后，基于安全考虑，可能更换appId，则旧的appId标记为停用，不要删掉；请求方和服务端都应记录接口交互情况，以便双方跟踪调查，其中appId属于重要依据。如果双方都有作为服务端的场景，则双方都需要各自管理分配appId。
接口版本号，是指对应接口文档的版本号。随着业务发展，可能某些接口增加了一些新的业务字段；为适应这种变化，双方请求和结果报文将采用json字符串格式；双方约定，已存在的字段定义不会轻易删除，一般只会新增字段，进行拓展。服务端新增了字段并更新启用，请求方仍能正常调用接口，只是不会用到那些新增字段；当请求方按照新的文档，也修改软件用上那些新增字段后，这些新字段才真正发挥作用。为方便双方跟踪调查，请求方调用接口时，写上对应接口文档的版本号。
请求示例(http请求的json串)：
{
"appId": "test123",
"version": "1.0",
"data": {
"dataType": "1"
}
}
|
2.3 响应报文格式
响应报文为json格式，内容格式如下：
参数名称
| 中文说明
| 类型
| 是否为空
| 参数说明
|
code
| 结果代号
| 字符
| 非空
| 200是成功，其他值是失败原因的各种细分
|
msg
| 结果描述
| 字符
| 非空
| 结果描述的详情，主要是失败原因描述
|
data
| 结果数据集
| 集合
|
| 由key/value组成的集合；不同场景有不同的约定，具体看接口详情
|
关于code结果代号，约定一些公共的编号如下，
code代号
| 对应msg含义
| 说明
|
200
| 成功
| 成功
|
800
| 无效的appId
| 失败
|
|
|
|
|
|
|
三位数以内的编号，用于公共约定，适合全部接口。四位数或更大数值的编号，用在具体业务场景，细分各种失败原因。建议每个接口的编号范围作一下规划，使得每个编号唯一，以便快速定位所在接口、失败原因。
json响应格式示例（成功）：
{
"code": "200",
"msg": "数据获取成功",
"data": {
"key": "value",
"list": [{
"name": "来电",
"id": "1"
},
{
"name": "来信",
"id": "2"
}
]
}
}
|
json响应格式示例（失败）：
{
"code": "60020",
"msg": "参数不能为空",
"data": null
}
|
3接口详情
3.1 工单查询
按工单ID查询工单信息。每次调用只查询一个工单。
3.1.1 请求地址
http://172.16.73.91/flowIntefaceCx/getFlowInfoById
3.1.2 请求参数
参数名称
| 参数含义
| 类型
| 必填
| 参数说明
|
id
| 工单号
| 整型
| 非空
| 工单的唯一标识
|
请求示例(http请求的json串，其中appId请写为实际值)：
{
"appId": "test123",
"version": "1.0",
"data": {
"id": 336940
}
}
|
